# API Key 账号鉴权：设计

> 状态：草案，待确认本文“待确认项”后实施。

## 目标与可测试验收标准

为 `POST /loan` 增加真实的 API Key 账号鉴权，在查询贷款数据前保证：

1. `apikey` 在账号存储中存在。
2. 该账号的 `status` 严格等于 `1`。
3. 使用该账号独立的 `secret` 验证请求签名。

可观察的验收标准：

- 已存在且 `status=1` 的 API Key 通过鉴权，继续现有时间戳、签名和贷款数据查询流程。
- API Key 不存在或对应账号 `status!=1` 时，终止请求，不查询贷款数据。
- 对外不区分“Key 不存在”和“账号被禁用”，避免泄露账号状态。
- `GET /health` 不受鉴权影响。
- 请求体字段、签名参数和签名算法不变。

## 当前实现与问题

- `app/Http/controllers/loan/index.go` 只校验 `apikey` 非空，随后将其纳入现有签名计算。
- 当前验签使用环境变量 `SECRET_KEY` 中的全局共享 secret，并没有实现每账号独立 secret。
- `app/middleware/auth.go` 的 `APIKeyAuth` 只读取 Query/Header，且没有挂载到 `/loan`；而当前公开契约中 `apikey`
  位于 JSON 请求体。
- 已启用的 MongoDB 是当前唯一持久化主调用链依赖；Redis 代码虽存在，但尚未启用；仓库中没有 MySQL
  配置、客户端或驱动依赖。
- 现有 `pkg/redis` 用 `context.Background()` 且将“Key 不存在”和“Redis 故障”都转成空值，不能直接用于需要
  明确降级语义的鉴权链路。
- 当前日志会记录完整请求体，其中包含 `phone`、`apikey` 和 `sign`。在鉴权上线前必须同步停止记录这些敏感原值。

## 方案及备选方案

### 推荐方案：内存 + Redis + MySQL 三层读取

MySQL 是账号的权威数据源，Redis 是跨实例二级缓存，每个 Airis 进程保有容量受限的一级内存缓存。
增加统一 `AccountStore` 边界，由 Loan Handler 在 JSON 绑定和基础参数校验后调用：

```text
POST /loan
  -> 绑定 JSON，校验必填项/类型/时间戳
  -> 对 apikey 做 SHA-256，仅作为缓存 Key
  -> L1 进程内存：命中则返回账号与加密 secret；未命中/过期/内部异常则读 L2
  -> L2 Redis：命中则回填 L1 并返回；未命中/异常则读 L3
  -> L3 MySQL：命中则回填 Redis 和内存；未命中则缓存短期负结果
  -> MySQL 未命中：拒绝；MySQL 故障：鉴权服务不可用并 fail closed
  -> status != 1：拒绝
  -> 解密该账号的 secret，验证现有请求签名
  -> 查询贷款数据并返回
```

不直接在现有 Gin 中间件中解析 JSON，避免重复读取/恢复 Body、重复 DTO 和改变现有请求契约。
账号查询通过小接口注入 Handler，以便用内存 fake 做 `httptest` 组件测试，不让组件测试依赖真实 Redis/MySQL。

“一层失败读下一层”中的失败仅指缓存未命中、过期、解析失败或依赖异常。已命中的 `status!=1` 是有效鉴权结果，
应立即拒绝，不得为寻找可能的启用值而继续向下查询。

### 备选方案

| 方案 | 不采用原因 |
| --- | --- |
| 将 API Key 改为 `X-API-Key` Header 并复用现有中间件 | 会改变已有 JSON 和签名契约，需客户端迁移 |
| 配置文件/环境变量静态白名单 | 状态变更需重启，账号增多后不易管理，也不适合审计 |
| 明文存储 `secret` | 数据库读权限或备份泄露时可直接伪造签名 |

## 数据模型与迁移

### MySQL 表（权威数据源）

```sql
CREATE TABLE api_accounts (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    account_id VARCHAR(64) NOT NULL,
    name VARCHAR(128) NOT NULL,
    apikey VARCHAR(64) NOT NULL,
    secret_ciphertext VARBINARY(256) NOT NULL,
    secret_nonce BINARY(12) NOT NULL,
    secret_key_version SMALLINT UNSIGNED NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_api_accounts_account_id (account_id),
    UNIQUE KEY uk_api_accounts_apikey (apikey)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- `account_id`：稳定账号标识，不使用手机号或 API Key。
- `apikey`：客户账号的凭据标识，可明文存储并建立唯一索引；仍按敏感标识处理，不记录到日志。
- `secret_ciphertext`：每账号独立 secret 的 AES-256-GCM 密文，包含认证标签；MySQL 不保存明文 secret。
- `secret_nonce`：本次加密的唯一 nonce，不是秘密，不得在同一主密钥下重用。
- `secret_key_version`：主密钥版本，用于主密钥轮换和分批重加密。
- `status`：严格使用整数；`1` 表示启用，其他值包括缺失均视为不可用。首期不扩展角色或接口级权限。
- `created_at`/`updated_at`：UTC 时间，用于追踪变更；不作为首期鉴权条件。

鉴权 SQL 必须使用参数化查询并通过 `apikey` 唯一索引命中单行：

```sql
SELECT account_id, secret_ciphertext, secret_nonce, secret_key_version, status, updated_at
FROM api_accounts
WHERE apikey = ?
LIMIT 1;
```

不把 `status` 合并到 SQL 条件，以便内部能区分“未知 Key”与“已禁用账号”；对外响应仍完全相同。

### Redis 和内存缓存

- Redis Key：`airis:auth:account:<sha256(apikey)>`，Value 仅包含 `account_id`、加密 secret 及其密钥版本、`status`、
  `updated_at` 和缓存格式版本，不包含明文 `apikey` 或 secret。
- 内存 Key 使用同一 `sha256(apikey)`，条目包含账号快照、加密 secret 和过期时间。实现必须并发安全且设置硬容量上限，
  防止随机 Key 攻击耗尽内存。
- 推荐初始值：L1 正向 TTL `10s`，Redis 正向 TTL `60s`，负结果 TTL `5s`；在未有容量和禁用生效
  SLA 前，这些只是可配置起点而非已确认指标。TTL 应加小比例随机抖动，避免集中过期。
- MySQL 查询成功后，先回填 Redis，再回填本地内存；回填失败不改变本次 MySQL 鉴权结果，但必须记录分类错误。
- MySQL 返回不存在时可回填短 TTL 负结果，防止随机 Key 穿透；负缓存也必须受 L1 容量上限约束。

上线前应提供可审查、非破坏性的 MySQL DDL 和账号 upsert 脚本。每账号 secret 应使用密码学安全随机源生成，
明文只在创建时对客户交付一次。

### API Key/Secret 生成与交付

`apikey` 是账号凭据标识，`secret` 是每账号独立的签名密钥。`apikey` 可从 MySQL 查询，secret 明文
只在创建或轮换时生成和对客户交付；MySQL 只能读到密文，服务端仅在鉴权过程中临时解密：

```text
受控的开通工具生成 apikey 和 32 字节高熵 secret
  -> 用服务端主密钥和唯一 nonce 加密 secret
  -> 将 apikey、secret 密文、nonce、密钥版本和 status 写入 MySQL
  -> 通过受控通道向客户展示 apikey + secret 一次
  -> 工具结束后不保留 secret 明文
```

- 优先使用内部管理平台的一次性展示页，或有访问审计、过期和撤回能力的密钥交付通道。
- 禁止通过普通聊天、邮件正文、工单、共享表格或请求日志交付 secret 或完整的 `apikey + secret`。
- 开通工具的普通标准输出、错误、Shell 历史、临时文件和审计日志都不得包含 secret 明文；
  唯一例外是明确的一次性交付界面。
- 不提供 secret 找回或再次展示接口。客户丢失 secret 后必须创建新凭据、完成客户端切换，再禁用旧凭据。
- 若需无中断轮换，数据模型需从“账号单凭据”改为“账号与凭据一对多”。

## 接口与兼容性

- 保持 `POST /loan` JSON 中 `apikey` 的位置、名称和签名参与方式不变。
- 保持现有“参数排序拼接 + `key=secret` + MD5”签名格式不变，但服务端验签密钥从全局
  `SECRET_KEY` 改为按 `apikey` 查得的账号独立 secret。这是行为变更，必须与现有客户端联合验证。
- 空 `apikey` 继续按现有参数错误处理。
- 对于非空但不存在或已禁用的 Key，推荐返回 HTTP `401`，JSON 响应保持 `status`/`msg`/`sid`/`data`
  形状，业务码复用 `ErrInvalidApikey (2001)`。该行为是新的对外鉴权契约，实施前需确认。
- L1/Redis 故障应无感降级到下一层；只有 MySQL 也超时或不可用时才整体 fail closed，不得绕过鉴权继续查询
  业务数据。推荐 HTTP `503` + `ErrServiceUnavailable (9002)`，不返回依赖原始错误；此错误契约也需实施前确认。

## 项目结构与代码风格

预计实施边界：

```text
app/Http/controllers/loan/       绑定请求、编排鉴权与业务查询
app/models/                      账号持久化模型
app/repositories/                内存、Redis、MySQL 分层实现及统一查询边界
pkg/config/                      MySQL、Redis、缓存 TTL/容量和超时配置
pkg/crypto/                      账号 secret 的加密、解密和主密钥版本选择
app/Http/controllers/loan/*_test.go
app/repositories/*_test.go       分层降级测试与隔离 Redis/MySQL 集成测试
```

缓存 Key 哈希使用标准库 `crypto/sha256`，secret 加密使用 `crypto/aes`、`crypto/cipher` 和
`crypto/rand`，MySQL 使用 `database/sql` 与审核后锁定版本的驱动，错误用 `%w` 保留原因。
当前 `go.mod` 没有 MySQL 驱动，因此实施会增加一个生产依赖，需单独评审其版本、许可证和安全维护状态。
数据访问接口保持最小，例如：

```go
type AccountStore interface {
	FindByAPIKey(ctx context.Context, apiKey string) (Account, error)
}

func (a Account) Enabled() bool {
	return a.Status == 1
}
```

## 错误、超时和可靠性

- 使用 `c.Request.Context()` 传递取消，并为 Redis 和 MySQL 分别设置子超时；不复用现有 Redis 封装中的
  `context.Background()`。
- 每层统一返回 `hit` / `not_found` / `dependency_error`，不得用空字符串合并不同状态。
- L1 错误或未命中继续 Redis；Redis 错误或未命中继续 MySQL。MySQL 查询失败时 fail closed。
- 缓存回填是 best effort，失败不覆盖 MySQL 已返回的鉴权结果。
- 不在同一请求中自动重试 MySQL，避免在故障时放大负载。
- 同一 Key 大量并发未命中时应合并回源，且请求等待必须可被 Context 取消，避免缓存击穿。
- 账号禁用操作顺序为：提交 MySQL `status` 更新 -> 删除 Redis Key -> 发布失效通知以删除各实例 L1。
  删除/通知失败时按 TTL 最终收敛，因此最大禁用延迟受 Redis TTL 限制。
- secret 轮换后也必须删除 Redis Key 并通知各实例删除 L1，防止继续使用旧密文验签。
- secret 密文无法解密、认证标签校验失败或密钥版本不可用时，必须按服务端安全错误 fail closed，
  不得降级为全局 `SECRET_KEY`。

## 安全与隐私

- MySQL 可存储明文 `apikey` 作为凭据标识，但日志、Redis Key 和 L1 Key 中不输出明文 `apikey`。
- MySQL、Redis、L1 和日志都不保存 secret 明文。L1/Redis 只缓存加密 secret，鉴权时才临时解密。
- AES-256-GCM 主密钥必须位于 MySQL/Redis 之外的受控密钥源，不得写入仓库、数据表或缓存。
  加密时应将 `account_id` 和 `apikey` 作为关联数据，防止密文被替换到其他账号。
- 同步修改请求日志，删除或遮罩 `phone`、`apikey`、`sign` 和响应业务数据。这是鉴权上线前置条件。
- 只记录鉴权结果类型、内部 `account_id`、路径、业务码和耗时；不记录请求凭据。
- 每账号 secret 应为至少 32 字节的高熵随机值，账号间绝不得共享。
- 现有 MD5 签名是已知安全风险，本次为保持客户端签名格式不主动改算法；服务端签名比较应改为常量时间比较。

## 性能与可观测性

- `apikey` 唯一索引保证 MySQL 单点查询，不扫描表。
- 缓存中保留密文，每次请求执行一次本地 AES-GCM 解密；上线前应计入鉴权耗时。
- 上线前需在代表性数据量下测量各层命中率、p50/p95/p99 鉴权耗时、MySQL QPS 和整体吞吐，
  当前没有可验证的延迟目标，不虚构数值门槛。
- 记录按结果分类的计数和耗时：`l1_hit`、`redis_hit`、`mysql_hit`、`key_not_found`、
  `account_disabled`、`l1_error`、`redis_error`、`mysql_error`、`decrypt_error`、`cache_backfill_error`；
  只有项目接入指标系统后才升级为 metrics，首期可使用不含凭据的结构化日志。
- 异常的未知 Key 比例可作为攻击或客户端配置错误信号，但不记录 Key 本身。

## 测试策略

- Unit：缓存 Key 哈希稳定性，secret 加解密、密文篡改、错误 nonce/密钥版本，账号独立 secret 验签，
  `status` 判定，L1 容量/TTL/并发安全，三层结果和错误分类。
- Layered store：覆盖 L1 命中、L1 miss -> Redis 命中、Redis miss/error -> MySQL 命中、MySQL not found、
  MySQL error、回填失败、负缓存、同 Key 并发回源合并和 Context 取消。
- Component（Gin `httptest`）：空 Key、未知 Key、禁用账号、启用账号、Redis 降级、MySQL 超时，
  并断言拒绝时不调用贷款数据查询。
- Contract：固定现有 JSON 请求字段、签名参数及成功响应，并固定确认后的鉴权失败响应。
- Integration：仅使用隔离 Redis DB/Key 前缀和 MySQL database，验证 `apikey` 唯一索引、精确查询、TTL、
  禁用/secret 轮换失效通知和依赖故障。
- Security：检查日志和缓存不出现明文 `apikey`、secret、`sign` 或完整 `phone`，并验证不得回退使用全局 secret。

## 风险、发布和回滚

### 主要风险

- 现有系统对 API Key 只校验非空，但仍要求使用全局 `SECRET_KEY` 生成有效签名；开启账号级强制鉴权后，
  未预先建账号或未切换到独立 secret 的客户端会立即失败。
- Redis 和 MySQL 成为新的鉴权运行时依赖；虽然 Redis 故障可降级，MySQL 故障会导致缓存未命中的鉴权请求失败。
- 缓存会使 `status` 变更存在短暂不一致；必须确认可接受的最大禁用生效时间，再确定 TTL。
- 随机无效 Key 可导致缓存穿透和内存污染；需要短负缓存和 L1 容量上限。
- 主密钥泄露会使所有账号 secret 可被解密；必须限制访问权限、记录密钥版本并具备轮换和重加密流程。
- 当前代码使用全局 `SECRET_KEY`；直接切换为账号独立 secret 会使仍使用旧全局 secret 的客户端签名失效。

### 发布顺序

1. 业务方确认允许访问的账号和客户端迁移窗口，不从现有请求日志导出凭据。
2. 审核 MySQL 驱动、主密钥来源与新增环境配置；在目标环境创建表和唯一索引。
3. 通过受控工具为每个账号生成独立 `apikey + secret`，写入 `apikey` 和加密 secret，一次性向客户交付。
4. 客户使用新的账号 secret 生成签名并完成联调。不得在账号查询或解密失败时回退到全局 secret。
5. 配置独立 Redis Key 前缀和最小权限 MySQL 账号，验证 Redis/MySQL 超时、连接池和加解密失败路径。
6. 发布日志脱敏、三层鉴权查询和测试；开放流量前验证各层命中、降级、禁用和 fail-closed。
7. 观察各层命中率/错误率、解密错误、Redis/MySQL 延迟和 `/loan` 总体延迟。

代码回滚到上一版即会恢复原有“API Key 仅校验非空 + 全局 `SECRET_KEY` 验签”行为，属于安全降级，需明确授权。
MySQL 表和 Redis Key 在回滚时保留并自然过期，
不做破坏性删除；待故障原因解决后可重新发布。

## 实施边界

- 总是执行：鉴权先于贷款数据查询；L1/Redis 异常继续下一层；MySQL 失败时 fail closed；不记录凭据；
  使用唯一索引和有界缓存；增加单元、分层降级、组件和契约测试。
- 先询问：修改 HTTP/业务码；新增 MySQL 驱动和运行时依赖；确定主密钥来源与轮换流程；确定 TTL/容量/禁用 SLA；扩展角色权限；
  增加管理接口；迁移或废弃现有 Key；执行任何目标环境脚本。
- 绝不执行：明文存储/记录 secret；鉴权依赖故障时放行或回退到全局 secret；运行 `cmd/init_mongo.go`
  或其等价重建操作；未确认客户端兼容前修改现有签名格式。

## 待确认项

1. AES-256-GCM 主密钥由专用 KMS/密钥管理服务提供，还是由受控环境变量注入？需要确定密钥版本、轮换和应急恢复方式。
2. 鉴权失败是否确认为 HTTP `401` + 业务码 `2001`，账号库不可用是否为 HTTP `503` + 业务码 `9002`？
3. MySQL 连接信息、数据库名和账号表名由哪些环境变量提供？是否确认表名为 `api_accounts`？
4. 最大可接受的账号禁用生效时间是多少？这会决定 L1/Redis TTL；本文的 `10s`/`60s` 只是推荐起点。
5. L1 最大条目数和目标单实例 QPS 是多少？未确认容量前不应将缓存大小写死。
6. 现有客户端是否仍使用全局 `SECRET_KEY`？首批账号凭据由谁审批、交付和组织切换？
7. 账号只需要单凭据，还是必须在首期支持无中断轮换（同账号同时存在新旧两组 `apikey + secret`）？
