# Spec 使用规范

本仓库使用 `doc/specs/` 存放 Spec。需求、设计和任务文档均直接放在该目录，目前不再按主题
创建更深子目录，也不得为填充索引生成空 Spec。

## 何时需要 Spec

以下任一情况通常先创建 Spec，再修改代码：

- 任务无法由不超过约 2 个文件的局部改动和直接测试完成。
- 修改公开 HTTP API、Proto、业务码、Mongo 文档格式或其他数据契约。
- 引入或升级生产依赖、数据库、缓存、外部服务或中间件。
- 修改架构、部署、安全、认证、性能、超时、重试或故障恢复策略。
- 涉及多个现有模块，或需要兼容、迁移、灰度、回滚方案。
- 需求有多个合理解释，且不同选择会产生不同外部行为。

纯文案修正、已明确的局部重命名、无行为变化的小范围格式修复通常不需要 Spec。是否属于简单
任务必须根据影响而不是代码行数判断。

## 命名

```text
YYYYMMDD-简要说明-文档类型.md
```

- 日期使用文件首次创建当天的本地日期，后续修改不变。
- 文档类型只能是 `需求`、`设计`、`任务`。
- 同一需求的三份文件使用相同日期和简要说明。
- 简要说明建议 2–20 个字符，不含空格、斜杠或特殊符号。
- 示例：`20260803-apikey验证-需求.md`。

只有实际需要某类文档时才创建；简单变更不要求机械生成三件套。

## 需求模板

```markdown
# 标题：需求

## 背景与事实来源
## 目标
## 范围
## 非目标
## 约束与待确认项
## 可测试验收标准
```

验收标准必须描述可观察行为，不写实现步骤，不发明未确认业务规则。

## 设计模板

```markdown
# 标题：设计

## 当前实现与问题
## 方案及备选方案
## 接口与兼容性
## 数据与迁移
## 错误、超时和可靠性
## 安全与隐私
## 性能与可观测性
## 风险、发布和回滚
## 待确认项
```

没有涉及的章节明确写“不适用”及理由；不得虚构部署平台、容量或监控能力。

## 任务模板

```markdown
# 标题：任务

## 依赖顺序
- [ ] 任务：目的、可能修改文件
  - 验收：可测试结果
  - 验证：仓库中真实可执行的命令

## 检查点
## 风险与阻塞项
```

每个任务应是可独立审查的最小切片，通常控制在 1–5 个文件；依赖、验收和验证命令必须明确。

## 生命周期

1. 创建前确认没有同主题有效 Spec。
2. 编写时引用代码、配置、测试或已确认文档；不确定项标记“待确认”。
3. 实施前由人工确认需求和关键设计选择。
4. 实施中若范围或契约变化，先更新 Spec，再继续代码修改。
5. 完成后记录验证结果和遗留风险；同步受影响的 Rules 与 Knowledge。
6. Spec 是单次变更记录，不自动升级为长期规则。
